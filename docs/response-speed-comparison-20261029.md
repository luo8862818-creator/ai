# Dify 与自定义聊天响应速度实测

日期：2026-10-29。通过浏览器 MCP 实际访问两个部署页面，使用新会话和相同问题对比。计时从浏览器发送请求开始，“首段”指首次接收到非空答案文字，“完成”指终止事件。工具调用进度不算答案文字。

| 问题 | 调用入口 | 首段文字 | 完成 |
| --- | --- | ---: | ---: |
| 如何进入系统设置页面？ | Dify 网页，18082 | 4.341 秒 | 5.355 秒 |
| 如何进入系统设置页面？ | 自定义网页，18084 | 7.116 秒 | 8.270 秒 |
| 如何进入系统设置页面？ | 直接调用公共 API，绕过 Java | 3.313 秒 | 4.344 秒 |
| 历史定位轨迹或设备详细状态 | Dify 网页，18082 | 6.173 秒 | 9.218 秒 |
| 历史定位轨迹或设备详细状态 | 自定义网页，18084 | 8.352 秒 | 9.301 秒 |

## 观察

- Dify 网页调用 `/api/chat-messages`，请求为 `response_mode: streaming`；Java 调用 `/v1/chat-messages`，Agent 模式同样使用流式请求。自定义网页接收到分段 `answer` 事件，并非一直等到完整答案才返回。
- 系统设置问题：Dify 网页调用了 `search_health_knowledge`；自定义程序先调用 `check_health_system_scope`，再调用 `search_health_knowledge`。两次 Agent 运行的执行路径不同，不能把约三秒差异全归因于 Java。
- 该次自定义请求，服务端首段耗时为 7101ms，浏览器接收到首段为 7116ms；服务端完成耗时为 8251ms，浏览器终止事件为 8270ms。事件送达没有出现秒级积压。
- 历史定位问题：Dify 网页调用了 `getAllPersonVitals`；自定义程序本次没有公开工具调用事件，直接要求补充人员、时间和设备信息。完整回复耗时仅相差约 83ms，但两次生成的内容、工具路径不同。
- 直接公共 API 调用 4.344 秒完成，表明本次测试中公开 API 本身也能快速回复。没有证据证明 Dify 给自带网页提供了专属推理加速。
- 本地配置的 API `/info` 返回 `name: demo`、`mode: agent`，`/parameters` 无必填输入。网页显示同样的名称和类型；仅凭名称不足以证明远端 Java 进程当前 API Key 对应的内部应用 ID 完全一致。

## 诊断定位

可以在服务器日志中查找以下自定义网页请求：

- 系统设置：`requestId=094a94c8-83e6-4d93-9741-c1aae5e0d111`
- 历史定位：`requestId=fcc04900-0e67-4875-a88e-5718614d50e3`

结合 `first_event`、`first_answer`、`tool`、`stream_summary` 查看上游等待、工具执行和完成时间。与浏览器收到事件的时间对比后，才能区分上游耗时和转发缓冲。

## 优化优先级与限制

1. 优先检查 Agent 提示词、工具描述和参数要求，让纯操作说明问题走知识库，让缺少人员及时间条件的问题先澄清，减少不必要的范围检查或全量人员查询。工具选择改变的是 Agent 执行路径，需要验证回答质量，不能仅为了提速跳过必要查询。
2. 对比已发布应用、模型配置、输入变量和新旧会话上下文。推理和工具选择存在波动，相同文字不保证相同执行路径。
3. 若出现“服务端很早生成答案、浏览器很晚收到”，再检查代理缓冲与压缩。本次未观察到该现象。
4. 前端更及时展示状态可改善等待感，但不会缩短上游模型推理及业务工具本身的执行时间。

这是顺序执行的少量实测，不是并发压测或长期平均值。服务负载、模型缓存、工具耗时可能变化。本次没有复现之前 180 秒超时的问题，也没有读取、修改 Agent 提示词或工具配置；没有改动生产程序。测量只保留事件类型、工具标识及耗时，没有保存原始思考内容或 API Key。
